## 2. 现状核实

### 2.1 现版额度拆借页（一期）

核实方法：只读代码，用仓库自带的接口打桩前端重绘，不起后端。改前截图在 `docs/delivery/2026-11-25-omc-quota-lending-revamp/before/`。codex 一组用运营负责人 11/23 09:00 的真实读数（卡名用夹具假名），commandcode 一组没有拿到真实读数，形状按反馈描述造，数字是示意。

1. 池块里文字全在 10～13 px；codex 一组约 290 字，其中结论句约 150 字；示意的 commandcode 一组约 600 字。页面只给「偏用 / 少用」两个标签，没有任何一处写「该设成几」。
2. 整池无法建议的条件：任一张卡缺长窗口、缺剩余、缺具体重置时刻或读数过期；可比较的卡窗口类型不止一种；页面时钟越过池里最早的读数鲜度界（前端会给每张卡补「读数已过期」）。冷却、需重新授权、读取失败、耗尽、剩余低于 10% 不属于以上三条，只让那张卡「受限」；可服务的卡不足两张时池标「无法给出偏用结论」，同样没有建议，只是叫法不同。
3. 「剩余低于 10%，不参与偏用排名」出现在没人排名的池里；「窗口类型不同」每张卡重复一遍。
4. 卡名是凭证文件名；OAuth 管理页大字是账号名，文件名是副名称（`web/src/components/authFiles/authFileLogic.ts` 的 `deriveAuthFileIdentity`）。
5. 凭证详情抽屉里把整个池块又画了一遍。

### 2.2 优先级相关的事实

CPA 怎么选卡的部分来自同目录的调研报告 `docs/delivery/2026-11-25-omc-quota-lending-revamp/research-priority.md`：读的是 CPA 的代码（2026-09-30 的提交 c3ce22a2，对照 v7.3.5 与 v8.0.74，调度核心一致），没有运行验证，也没有读线上。

| 事实 | 结果 | 依据 |
|---|---|---|
| 数值方向与相对性 | 整数，数大先选，未设按 0，负数合法；比较范围是「同一个模型所有就绪的凭证」，不分池、不分套餐，同一个模型登记在两家以上才跨 provider 比 | 调研报告附录 B |
| 档与档之间 | 只有最高的就绪档有流量，低档闲置；**CPA 不看额度百分比，只在上游返回 429 后才知道一张卡耗尽**：高档卡被拒绝后，同一次请求当场转到低档卡，高档卡冷却到上游声明的重置时刻，回满后第一个请求起自动切回，不用再改 | 调研报告附录 B、E |
| 同一档里 | 默认 round-robin 轮流；fill-first 用文件名字典序第一张；只有 weighted-round-robin 才读权重。策略是全局开关，一个开关管所有池 | 调研报告附录 B、F |
| 会话亲和 | 默认关；开着时已绑定的会话盖过优先级，绑定 1 小时，每次用到就续期 | 调研报告附录 B |
| 改完何时生效 | 管理接口改完，下一次选卡就用新值，不用重启；插件虚拟凭证改不了（409） | 调研报告附录 B、C |
| 哪些凭证能设 | 文件凭证、插件认证文件（v7.3.5 不读 priority，之后的版本读）、API key 条目（条目级）、兼容条目（只能条目级，key 只有权重）；插件虚拟凭证不能直接改 | 调研报告附录 C |
| OMC 能显示、能改 | 能。凭证详情「配置」页有「优先级」「调度权重」输入，数值可正可负；OAuth 管理页每张卡可带「优先级 n」「权重 n」小标签（值为 0 不显示），列表可按优先级、权重排序 | `web/src/components/authFiles/AuthFileDetailDrawer.tsx`；`web/src/pages/oauthManagement/OAuthCredentialRecord.tsx`；调研报告附录 D |
| 额度拆借页数据里有没有现在的优先级 | 没有。后端拿额度概览的那一层手里本来带着优先级和权重，投影成拆借数据时没带 | `internal/api/quota_lending.go`；调研报告附录 D |
| OMC 写入的保护与缺口 | 写串行、字段白名单与范围校验、写前写后各记一条审计、写后回读核对。没有：批量、改前快照与撤回、审计里的新旧数字、写前二次确认、角色分级；控制台这条路径没有比较并交换；CPA 写盘失败也会回成功 | `internal/api/management_auth_file_fields.go`；调研报告附录 B、D、F |
| 一期的决定与项目边界 | 一期 q01 的选项是「只提示，不改路由」，没有找到运营负责人的答复，一期按推荐只提示实现；项目定义写着「不做自动路由，不进 CPA 请求路径」（出自模型分组的范围决定，没有提写优先级）；二期（人工确认后写权重，带快照、回滚、审计、熔断）已设计，暂缓、属红线，开工前必须运营负责人本人点头 | 调研报告附录 F |

### 2.3 一期排序依据在 CPA 硬切档下的表现（模拟）

CPA 的优先级是硬切档，排前面的卡接下全部请求，用得快；一期按「重置前日均可用」排先后，算出来的先后会很快翻过来。按两张 codex 卡的例子模拟（4 天）：一个点的门槛下，每天共用 20% 时约改 4 次，每天共用 40% 时约改 39 次；门槛放到 3 个点，约 1 次、约 18 次。改一次要在每张要改的卡的详情里各改一遍。按下一次回满的先后排，只在有卡回满时才变（例子里 4 天 2 次）。模拟里的用量与两张卡套餐一样大都是假设，不是真实用量。

### 2.4 还没有核实的

- 线上 CPA 是哪个版本、`routing.strategy` 与会话亲和现在的值（资料里记的目标配置是加权轮询加关闭会话亲和，2026-11-10 的记录，没有核对线上是否生效）：缺线上只读核对，页面里按「未核对」写。
- 池外是否有同一个模型的凭证、有几张、现在是几：缺线上凭证列表。
- 两张卡的真实套餐大小与真实请求需求：缺用量数据，评审页里每天共用 20%、40% 都标假设。
- 每张卡「现在的优先级」：评审页里一律标「假设」，页面上线后读到什么就是什么。
- 二期的设计草稿是否已并入主线；两张 codex 卡的 websocket 开关（开关不同时 Codex 可能越过档位）。

## 3. 范围

要的是：页面给出每张凭证在 CPA 里应该设成的具体优先级，一个能直接填的数值，和现在的数字并排，由运营人员照着自己去设。

**做**（页面只给建议，不写 CPA）：

- 额度拆借页：每个池一眼读到「每张卡现在是几 → 建议设成几」，哪些要改、哪些不用改；主屏小字收进「看依据」。
- 讲清设成建议值以后请求怎么走（含被拒绝才让位、没用的额度作废这些后果）、什么时候该再改一次（每次有卡回满先后翻过来）。
- 池里暂不参与的卡、不在任何池里的卡：不给建议数字，现在是几还是几。
- 同一个模型被池外的卡一起供货时：建议值只往下压，并写一句提醒，点开列出这些卡和它们现在的数字（哪些卡算池外的卡，见同目录 PRD 的第 5.7 节）。
- 要改的卡旁边放只带路的「去设置」，不提供「应用」。
- OAuth 管理页页头入口（只改文字）、凭证详情里的拆借块、窄屏与浅深色。

**不做**：

- 页面不写 CPA、不改路由，不做一键写入。
- 不新增上游采集，不改额度预测、单卡状态、通知，不改一期的 OAuth 列表行（偏用 / 少用小标签除外，见同目录 PRD 的第 4.1 节）、倒计时、快重置标记与排序。
- 不引入「卡别名」这类新功能。

## 4. 决定

五项决定均已定，取评审页上的推荐项（出处：2026-11-26 运营负责人的答复，见第 1 节）。每项决定当时的选项图和未采用的方案留在评审页。这些决定改了一期哪些验收规则，见同目录 PRD 的第 4 节。

| 编号 | 问题 | 定了 | 理由 | 代价 |
|---|---|---|---|---|
| D1 | 谁排前面，按什么排 | A 回满得晚的先用 | 与运营负责人 11/23 说的用法一致（多用回满晚的卡，让回满早的卡撑到回满），先后只在有卡回满时才变，不用每隔几小时改一次 | 被省着的那张卡没用的额度回满时作废，回满晚的卡最先被用掉 |
| D2 | 页面只给数字，还是再往前一步 | B 给建议数字，要改的卡旁边放「去设置」；一键写入不做 | 「去设置」只是带路，数字由运营人员自己填、自己保存，页面仍然只提示、不改路由，项目边界不用动，又省掉在列表里一张张找卡 | 每张卡仍要自己填一次、保存一次 |
| D3 | 读数不全、余量低的卡怎么办 | A 能比的先给数字，其余的卡不动 | 能给的先给，给不了的不挡路；页面不知道情况的卡，不去乱改它的数字，改动最少 | 不动的卡可能恰好最宽裕，先后只在能比的卡里排，页面会写明 |
| D4 | 数字往哪个方向改，才不误伤池外的卡 | A 只往下压：排第一的卡拿这一组现在最大的数字，往后每名减 10 | 排第一的卡拿的是这一组现在最大的数字，不会比现在更高，所以不会把池外没设数字的卡挡在后面；它本来就是最大的就不用动，要改的卡最少 | 数字会出现负数；排后面的卡要等前面的卡被上游拒绝才轮到，别的卡都能用时它一点请求也没有，回满前的余量会放着 |
| D5 | 卡名怎么叫 | A 和 OAuth 页同一个叫法 | 同一张卡两页叫法一致，不新增任何功能 | 额度拆借页要多拿一项账号名；没有账号的卡仍是文件名，可能还是长，所以要省略 |
